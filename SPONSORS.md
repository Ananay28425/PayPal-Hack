# Sponsor implementation ledger

Goal: all ten sponsors have a useful, inspectable contribution to one Assembly Proof journey. A sponsor is complete only when its actual tool is exercised, it changes a real product or engineering result, and a judge can reproduce that result. The table records **current truth**, not intended eligibility.

| Sponsor | Exact contribution | Current state | Reproducible completion evidence |
|---|---|---|---|
| AG Grid | Compare candidate products against each failed rule; clicking a row opens the evidence for that exact variant. | Not integrated. Local UI uses native HTML. | AG Grid package or Studio embed running, with linked selection and evidence. |
| APIMatic | Use PayPal Context Plugin to check the create/get/capture adapter and derive a negative-case regression. | Not integrated. Current adapter follows official PayPal docs. | Saved plugin-assisted change and regression test; no invented runtime dependency. |
| Astropods | Host bounded requirement extraction that emits typed proposals and trace IDs. | Not integrated. AI extraction currently runs inside FastAPI. | Real authenticated deployment and a trace for one UI proposal. |
| Bryntum | Model delivery and setup dependencies; a changed deadline or missing component changes readiness. | Not integrated. Current product checks only technical capacity. | Real schedule component affecting a rule with a visible before/after. |
| Channel3 | Discover exact product variants, then let the user choose an owned merchant offer. | Not integrated. Catalogue is invented. | Real product response saved with variant and provenance; no claim of retailer payment authority. |
| Elastic | Search source-backed product facts and show which passage supports a compatibility conclusion. | Not integrated. Current rules use explicit synthetic attributes. | Indexed evidence, query, and a result that changes or explains a decision. |
| Kernel | Inspect permitted source pages for a missing critical specification and retain a trace for review. | Not integrated. | Recorded browser observation tied to a specific fact, with unknown remaining if evidence is insufficient. |
| Postman | Run the owned mock purchase lifecycle and negative checks through an executable collection. | Collection implemented; runner execution still to verify in Postman. | Import collection, run requests, confirm tests pass. |
| Render | Host the API, static UI and bounded reconciliation worker with explicit sandbox configuration. | Dockerfile and `render.yaml` implemented; no Render deployment yet. | Public hosted URL plus live health, AI, and sandbox checkout evidence. |
| Zapier | Create an approved setup task only after a verified capture and explicit customer consent. | Not integrated; fulfillment absent. | One real scoped action and remote task ID, with replay-safe handling. |

Integrations must keep AI and evidence services outside payment authority. If a sponsor is unavailable, the frozen purchase and unresolved payment must still be inspectable. Prioritize the real PayPal Sandbox and AI demo before optional UI polish. No product result currently proves reduced merchant losses or first-prize odds.
